>
> - 필수 요구: 아키텍처 다이어그램, 외부 접속 방식 A 또는 B, 트러블슈팅 보고서, 실습 종료 후 리소스 정리 체크리스트.
> - 선택 보너스: HTTPS, Docker. 두 보너스의 실제 실행은 완료했고 텍스트 검증값을 별도 기록했다.

## 1. 방식 A(브라우저 접속)의 선택 이유와 검증 — 사전평가 #8 및 #2

**[실제 실행·화면 검증]** 과제에서 외부 접속 증명은 (A) 브라우저에서 `http://<퍼블릭IP>`를 여는 방식과 (B) `GET http://<퍼블릭IP>/health` 방식 중 하나를 선택하도록 했다. 이번 실습에서는 **A**를 선택했다.

**[설계상 이유]** B1-1에서 만든 **실제 포트폴리오**를 다른 기기(휴대전화 Chrome)에서 열고, HTML·CSS·JavaScript가 사용자에게 표시되는 것을 직접 확인할 수 있기 때문이다. 단순한 200 응답과 달리 디자인·정적 자산 제공을 확인하는 데 유리하다. Nginx와 Docker 실습 결과를 하나의 서비스로 이어 보여줄 수 있었다.

**[요청 흐름]**

```text
휴대전화 Chrome
   │  HTTP TCP 80  /  (보너스) HTTPS TCP 443
   ▼
인터넷 → Internet Gateway
   ▼
VPC b31-vpc (10.10.0.0/16)
   ▼
Public Subnet b31-subnet-public1-ap-northeast-2a
   └─ b31-rtb-public: 0.0.0.0/0 → IGW (활성)
   ▼
Security Group b31-web-sg: HTTP 80 / HTTPS 443 허용
   ▼
EC2 b31-web · 43.202.56.199 (실습 당시 공인 IP)
   ▼
호스트 Nginx (:80, :443 · TLS는 Let's Encrypt)
   ▼
127.0.0.1:8080 (호스트 Nginx 리버스 프록시)
   ▼
Docker b31-docker · nginx:alpine · 컨테이너 :80
   ▼
/var/www/html의 B1-1 포트폴리오 정적 파일
```

**[실제 증거]**
- 공인 IP에 접속하여 웹 포트폴리오 렌더링 확인: `http://43.202.56.199/` (실습 당시)
- 외부 도메인에서 HTTPS 포트폴리오 렌더링 확인: `https://codyssey-b31-web.duckdns.org/`
- 호스트 `curl -I http://localhost/` → `HTTP/1.1 200 OK`
- 컨테이너 `curl -I http://localhost:8080/` → `HTTP/1.1 200 OK`
- 추가 점검용 `curl -i https://codyssey-b31-web.duckdns.org/health` → `HTTP/1.1 200 OK`, 본문 `ok`
- 별도의 [실행 7항목 검증](validation-2026-11-22.md) 및 [AWS 라우팅 콘솔 실측](network-console-verification-2026-11-22.md)에 결과 기록.

**[한계]** `/health`는 **호스트 Nginx가 바로 `ok`를 반환**하도록 구성했으므로 Docker 컨테이너 내부의 정상 상태까지 보장하지 않는다. Docker의 작동 여부는 `docker ps`, `localhost:8080`의 200 및 로그로 별도 검증했다.

## 2. HTTPS 443번을 전 세계 IPv4에 공개한 이유·위험·대안 — #7, #12

**[실제 실행·화면 검증]** 보안 그룹 `b31-web-sg`의 인바운드 규칙은 공개 웹 포트 **HTTP TCP 80**, **HTTPS TCP 443**에 대해 `0.0.0.0/0`을 허용하도록 구성했고, SSH TCP 22는 제한된 접속 출처를 사용했다. Ubuntu Nginx에서 443 수신 및 Let's Encrypt 인증서 적용 성공을 확인했으며, `certbot certificates` 출력에 도메인 인증서가 유효한 것으로 표시됐다.

**[설계상 이유]** `0.0.0.0/0`은 임의의 IPv4에서 **해당 특정 포트로 접속할 수 있게 한다**는 의미다. 외부 누구나 사용하는 공개 HTTPS 웹사이트의 443번 포트라면 의도된 설계다. `0.0.0.0/0`으로 **모든 포트**를 개방하는 설정과 다르다. SSH 22는 관리 기능이므로 출처 제한을 유지한다.

**[위험]** 443을 전 세계에 공개하면 HTTPS를 사용하는 정상 방문자뿐 아니라 자동 스캐너, 반복 요청, 악의적 요청도 **웹 서비스의 공개 진입점**에 접근할 수 있다. TLS 인증서는 통신 암호화·서버 인증을 제공하지만 웹 애플리케이션 취약점, 취약한 인증, DDoS나 과도한 트래픽을 자동으로 해결하지 않는다.

**[현재 확인한 완화 조치]**
- SSH 관리용 22번을 전체 IPv4에 공개하지 않고 제한된 출처로 운영함
- 443에서 호스트 Nginx가 유효한 TLS 인증서를 제공함
- Docker의 8080 포트는 EC2 보안 그룹의 외부 인바운드에 별도 허용 규칙을 추가하지 않음
- `/health`로 호스트 응답을 확인할 수 있음

**[향후 개선 방안 — 아직 적용하지 않음]**
- Nginx/Ubuntu/Docker 이미지의 보안 업데이트와 접근 로그·오류 로그 주기적 확인
- Nginx 요청 제한(rate limiting) 및 적절한 HTTP 보안 헤더 검토
- 규모가 커질 경우 CloudFront나 ALB 앞단과 AWS WAF 등을 검토. 이 서비스들은 **추가 사용 요금이 발생할 수 있으므로 이번 무료·저비용 실습에서는 도입하지 않음**
- 서비스가 외부 공개용이 아니라 내부 사용자용으로 바뀐다면 VPN·허용 IP·인증을 통해 **443 접속원도 제한**하는 설계 검토
- Docker 포트는 현재 `-p 8080:80`으로 호스트의 여러 인터페이스에 바인딩돼 있음. 외부 보안 그룹은 8080을 허용하지 않지만, 향후 컨테이너 재구성 시 `-p 127.0.0.1:8080:80`처럼 루프백으로 제한하는 방안을 검토할 수 있음

**[검증 범위]** 443 인바운드 규칙은 실습의 콘솔 변경 화면과 실제 접속 결과를 바탕으로 기록했다. 방화벽·운영체제의 모든 규칙 및 WAF 설치를 검증했다고 확대 해석하지 않는다.

## 3. IAM과 Security Group 역할 구분 및 최소 권한 부여 절차 — #11, #15

**[실제 확인]**
- 실습용 IAM 사용자 `b31-learner`를 사용했고, EC2 Instance Connect로 Ubuntu 서버에 접속했다.
- IAM 정책 목록 화면에서 `iam:ListPolicies`를 시도했을 때 **`no identity-based policy allows the action`** 오류로 접근 거부됨.
- [IAM 실제 접근 거부 증빙](iam-permission-verification-2026-11-22.md)에 기록했다.

**[설계상 원칙]**
- **IAM**: 콘솔·API에서 AWS 자원을 **생성, 조회, 수정, 종료**하는 주체의 권한을 관리한다.
- **Security Group**: 이미 실행 중인 EC2 등에 들어오고 나가는 **네트워크 트래픽**의 포트·출처를 관리한다.
- 웹사이트를 방문하는 사람에게 `iam:ListPolicies`가 필요한 것은 아니다. 반대로 IAM에서 EC2 수정 권한이 있어도 보안 그룹의 SSH 22 인바운드 제한이 자동으로 없어지는 것은 아니다.

**[최소 권한을 단계적으로 적용하는 방법 — 원칙과 후속 검증 계획]**
1. 실습에서 필요한 작업을 목록으로 적는다: VPC·서브넷·라우팅·보안 그룹 조회·구성, EC2 시작과 상태 확인, Instance Connect 접속.
2. 먼저 **조회 권한**과 필요한 범위의 **생성·수정 권한**만 구분해 정책을 만든다. 일부 AWS `Describe/List` 작업은 리소스 ARN 조건을 지원하지 않으므로 각 작업별 지원 범위를 확인한다.
3. 특정 VPC·EC2 등에 제한이 가능한 작업은 리소스 ARN 및 조건 키를 검토한다. **`Resource: "*"`를 모든 작업에 일괄 적용하지 않고**, 필요한 AWS API에 대해서만 검토한다.
4. IAM 실습 사용자에게 정책을 연결해 작업을 시도하고, AccessDenied가 발생하면 **실제 거부된 API·리소스·조건**을 확인한다.
5. 그 작업이 과제에 반드시 필요할 때에만 해당 권한을 좁게 추가하고 다시 시험한다. S3·RDS·IAM 전체 관리 등의 불필요한 권한을 임의로 추가하지 않는다.
6. 실습 종료 후 필요 없어진 권한과 임시 자격증명을 정리한다. 실제 정책 전체 JSON은 관리자 권한으로 검토해야 한다.

**[실제 정책 검증의 한계]** `B31PracticePolicy`의 **전체 정책 JSON과 연결된 허용 Action 목록**은 아직 관리자 계정에서 확인하지 않았다. `iam:ListPolicies` 거부 **한 건**만으로 AWS 전 영역에서 최소 권한이 충족됐다고 결론 내리지 않는다. 이 내용은 적용·검증한 사실과 향후 절차를 구별하기 위해 명시한다.

## 4. 장애 발생 시 점검 순서: 라우팅 → 보안 그룹 → IP → 서버 → Docker/브라우저 — #14

**[현장 점검 순서 — 체크리스트]**

1. **VPC/서브넷/라우팅**: EC2가 과제 VPC와 퍼블릭 서브넷에 있는지 확인한다. `b31-rtb-public`에 `10.10.0.0/16 → local`, `0.0.0.0/0 → IGW`가 활성이고 서브넷과 **명시적 연결**됐는지 확인한다. Linux의 `ip route` 결과와 AWS VPC 라우트를 구분한다.
2. **Security Group과 네트워크 접근 제어**: HTTP 80 / HTTPS 443 인바운드가 필요한 대상에 허용됐는지 확인한다. SSH 22는 승인된 출처로 제한한다. 문제가 지속되면 NACL 등 별도 정책도 확인한다.
3. **인스턴스 주소와 DNS**: EC2가 실행 중이고 공인 IPv4가 할당돼 있는지 확인한다. `43.202.56.199`는 실습 당시 IP이므로 중지/시작 후 바뀔 수 있다. DuckDNS 현재 IP가 실제 EC2 공인 IP와 같은지 비교한다.
4. **호스트 서비스**: `sudo systemctl is-active nginx`, `sudo ss -lntp`, `curl -I http://localhost/`, `sudo nginx -t`로 서비스·수신 포트·응답·설정을 확인한다.
5. **Docker 및 프록시**: `sudo systemctl is-active docker`, `sudo docker ps`, `curl -I http://localhost:8080/`, `sudo docker logs --tail 20 b31-docker` 순서로 확인한다. Nginx 프록시가 `127.0.0.1:8080`으로 향하는지 확인한다.
6. **HTTPS/브라우저**: `curl -i https://codyssey-b31-web.duckdns.org/health`, `sudo certbot certificates`, 실제 외부 브라우저를 차례대로 확인한다. 요청 주소가 `http`인지 `https`인지와 포트 80/443을 구분한다.

**[실제 장애 사례]** 실습 중 호스트의 `curl -I http://localhost`는 `200 OK`였지만 Chrome에서 공인 IP 접속 시 `ERR_TIMED_OUT`이 발생했다. Chrome `net-export` 기록에서 443번으로 연결한 흔적이 확인됐고, HTTPS 업그레이드와 관련된 Chrome 실험 기능을 변경한 후 공인 IP의 HTTP 접속에 성공했다. 이후 DuckDNS 및 HTTPS를 별도로 적용했다. [실제 오류·가설·검증·조치·결과·재발 방지 보고서](troubleshooting.md)를 참고한다.

**[실제 별도 점검]** 19:16 KST의 [7항목 종합 검증](validation-2026-11-22.md)에서 호스트 및 Docker가 `active`, 두 로컬 HTTP 주소가 200, HTTPS `/health`가 `200 OK` 및 `ok`, 인증서가 유효한 것으로 확인됐다.

## 5. 단일 EC2의 병목 지표, ALB 도입 기준, 비용 관리 — #16

**[실제 구성]** 지금은 **t3.micro EC2 한 대**, 호스트 Nginx 한 개, Docker의 `nginx:alpine` 컨테이너 한 개로 정적 포트폴리오를 서비스한다. **ALB·Auto Scaling·RDS·WAF는 이번 배포에 설치했다는 증거가 없으며 사용한 구성으로 기록하지 않는다.** AWS VPC 대시보드 당시 NAT Gateway 0개도 확인됐다.

**[병목 확인에 유용한 지표 — 점검 계획]**
- **CPU 사용률/CPU 크레딧**: t3.micro의 CPU 지속 사용과 크레딧 잔액 추이를 확인한다.
- **메모리**: Ubuntu의 `free -h`, `top` 등을 사용해 메모리 압박과 OOM 여부를 확인한다.
- **네트워크/응답**: CloudWatch NetworkIn/NetworkOut, 웹서버 요청 수, 4xx/5xx 비율, 응답 시간, 연결 수를 추적한다. Nginx 로그 및 필요 시 추가 모니터링 수집이 필요하다.
- **디스크**: `df -h`와 EBS 여유 공간·I/O를 확인한다.
- **가용성**: HTTPS `/health`의 200 응답, 외부 브라우저 접속 및 장애 발생 시 복구 소요 시간을 확인한다.

**[ALB 도입을 고려할 상황 — 확장 설계, 이번 실습에서는 미적용]**
- 동시 요청 증가로 단일 인스턴스의 CPU/메모리·응답 시간·오류율이 지속적으로 나빠지고 수직 확장만으로 대응하기 어려울 때
- 무중단 배포 또는 여러 인스턴스 간 요청 분산과 대상 그룹의 상태 검사·장애 격리가 필요할 때
- 실제로 구성하면 `인터넷 → ALB(80/443) → 대상 그룹 → 복수 EC2`의 형태로 바뀐다. 이때 ALB 헬스체크는 **해당 대상 서버의 실제 동작을 검증하는 경로**로 설계해야 하며, 현재 호스트 Nginx의 정적 `/health`가 Docker 정상 상태까지 검사하는 것은 아니다.

**[비용 추적·정리 방안]**
- AWS 비용은 인스턴스 컴퓨트 시간 외에 EBS, 사용 중인 공개 IPv4, 네트워크 전송 및 도입한 부가 서비스 등에서 발생할 수 있다.
- 비용을 줄이기 위해 과제에서 필요한 **단일 EC2 구조를 유지**하고, 실측 필요성이 없는 ALB·NAT Gateway·RDS 등 유료 자원을 추가하지 않는다.
- 주기적으로 **Billing/Cost Explorer 및 서비스별 리소스 목록**을 확인한다. 실습 계정 `b31-learner`에서는 Billing 접근 권한이 제한될 수 있으므로 해당 조회가 필요한 경우 **관리자 계정으로 별도 확인**해야 한다.
- 자원 정리 때 EC2의 **Terminate 확인**, EBS 잔여 볼륨, Elastic IP 할당 여부, Internet Gateway, VPC·서브넷·라우팅 테이블·보안 그룹, NAT/ALB/RDS 생성 여부 및 Billing을 순서대로 확인한다. [현재 정리 체크리스트](cleanup-checklist.md)에는 **사용자 요청에 따라 삭제 보류**로 기록했다.
